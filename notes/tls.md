# TLS
1. Certificate Authority (CA) has a Public and a Private Key
- Has a Self-Signed Cerificate. This affirms the identity of this particular certificate authority. Public Key
2. Server wants to acquire a Certificate
3. Sever generates a Public and Private Key
4. Server generates a Certificate Signing Request (CSR - used to request an actual certificate)
- CSR contains Server's Public Key
- CSR is signed by Server's Private Key
5. Server gives signed CSR to CA
6. CA inspects and validates info in CSR
7. CA creates Certificate using info from CSR
8. CA signs Certificate using CA's Private Key
9. CA gives certificate to server
10. Server can then provide certi to prove its identity
11. Client wants to connect to the server securely
12. Clients already have CA Certificates installed
13. Client request Server's certi
14. Client validates certi is legitimate
15. Client validates that Server truly owns Certificate
- Client validates Server's certi in the SSL/TLS Handshake
SSL/TLS Handshake produces Session Keys:
- Symmetric Encryption
- Message Authentication Code (MAC)
* Session Keys form a Secure Tunnel to protect communication
# TLS Handshake
* Create the "protected tunnel" between Client and Server
1. Client Hello
* Version: Highest version of TLS/SSL Client Supports
* Random Number (32 bytes - 256 bits): Generated by the client. The first four bytes include the timestamp (down to the second) -> makes it impossible for 2 client hello send more than a second apart to have duplicate random number
* Session ID (8 bytes): Used to identify the specific session.
* Cipher Suites: List of Cipher Suites Client supports
* Extensions: Optional additional features added to TLS/SSL
2. Server Hello: Same 5 fields:
* Version: Highest version of TLS/SSL Server Supports
* Random Number (32 bytes - 256 bits): Generated by the server. The first four bytes include the timestamp (down to the second)
* Session ID (8 bytes): Value generated by Server to identify ensuing Session Keys
* Cipher Suites: Cipher Suite selected by Server
* Extensions: Optional additional features added to TLS/SSL
* Both know each other's random number (Both the client and the server know both random numbers).
* Both know the Session ID
* Both know the Cipher Suite
3. Certificate (sent by the server):
* Server certificate and full certificate chain
* The client attain two new info: certificate and public key
4. Server Hello Done:
* Indicates server has nothing more to send atm
* Other variants require server to send more
5. Client Key Exchange:
* Establish mutual keying material
* Proves server is true owner of certificate
* Done using Pre-Master-Secret (sent encrypted)
* Client generates Pre-Master-Secret
- 2 bytes: TLS/SSL Version
- 46 bytes: Randomly generated
* Pre-Master-Secret is encrypted with Server's Public Key
* At this point, both parties have identical Session Keys
* Neither of them know the other has the correct keys
* Rest of the handshake will prove to both parties that the other has the correct session keys
6. Change Cipher Spec:
* Indicates Client has everything necessary to speak securely
7. Finished:
* Proves to the Server that Client has correct Session Keys
* Client calculates Hash of all Handshake Records so far (5 - Client Hello, Server Hello, Certificate, Server Hello Done, Client Key Exchange)
* Combined with other values to create verification data, which will be encrypted with client session keys
* Server verifies with Server's copy of Client Session Keys
8. Server send Change Cipher Spec and Finished message
